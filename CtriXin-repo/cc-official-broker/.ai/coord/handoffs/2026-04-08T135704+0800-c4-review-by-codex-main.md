# C4 Sticky Runtime Binding Review

- reviewer: `codex-main`
- worker: `minimax2.7`
- verdict: `review_blocked`
- scope: `src/runtime/runtimeBindingStore.mjs`, `src/runtime/runtimeBinder.mjs`, `src/broker/stubServer.mjs`, `docs/STICKY_BINDING.md`

## Blocking Findings

1. `stubServer` 没有把 binder 的 fail-fast 结果转成失败响应。
   - `src/broker/stubServer.mjs:1680` 起，direct-connect 即使 `bindingResult.runtime === null` 仍然 `state.sessions.set(...)` 并返回 `200`。
   - `src/broker/stubServer.mjs:1833` 起，standard create/resume 同样无条件创建/覆盖 session 并返回 `200`。

2. `resume` 在 runtime 已不健康时仍保留旧 `remoteService`。
   - `src/broker/stubServer.mjs:1844` 会优先复用 `previous.remoteService`，即使本轮 binder 已返回 `bound_runtime_not_acceptable`。
   - 结果是上层看到 `runtime.binding` 失败事件，但 session 语义仍像成功恢复。

3. 文档与“最小闭环已落地”的口径不一致。
   - `docs/STICKY_BINDING.md:70` 明写“binding 失败不阻止 session 创建”。
   - 这和本轮宣称的“runtime unhealthy 时 fail-fast”冲突。

## Validation

### Local repro A
- 创建 session `sess-a` 成功后，把唯一 runtime 改成 `unhealthy=true`。
- 再调用 `POST /sessions` + `mode=resume`。
- 实际结果：HTTP 仍返回 `200`，`session.resume` 事件照常出现，旧 `remoteService.runtime_id=cc-static-1` 仍留在 session state。

### Local repro B
- 启动时让唯一 runtime 直接处于 `unhealthy=true`。
- 调用 `POST /sessions` 创建新 session。
- 实际结果：HTTP 仍返回 `200`，但 `runtime.binding.reason=no_healthy_runtime_available`。

## Revision Target

- 当 `bindingResult.runtime === null` 时：
  - `POST /sessions` create/resume/direct-connect 必须直接返回明确错误，不创建/覆盖 session；
  - 返回码至少区分：`no_healthy_runtime_available` vs `bound_runtime_not_acceptable`；
  - 不得保留旧 `remoteService` 伪装成成功 resume。
- `docs/STICKY_BINDING.md` 要同步改成真实语义。
- 通过后再补评分与验收状态。
